# Project brief: Personal Security

## Purpose

Make practical digital protection accessible to anyone—not only people who know how to administer computers. AI makes it easier to produce convincing impersonation and scale scams; this project uses AI to make the protective response clearer and more manageable. Avoid unsupported claims that every threat is worsening, and never sell fear or perfect safety.

**Promise:** help people take the next useful security step, without handing over their secrets or losing access to their lives.

## One workflow, separate delivery layers

- **Everyone:** a self-contained guide for the AI chat they already use. Upload or paste it, then say “Help me secure my digital life.” No terminal, special subscription, API key or connector required by the project.
- **Developers:** an inspectable `SKILL.md` package for compatible coding agents, with the same recovery, consent and evidence rules. Tools can reduce manual work, but are not required and do not expand permission.

Neither group is a second-class version. Delivery host, preferred explanation depth and relevant technical responsibilities are three independent dimensions. A developer can use ordinary chat; a nondeveloper can understand 2FA; neither identity implies permission or security expertise. The difference in tool access is who can observe a setting, not how much protection the person deserves. Chat-only progress is accurately labelled user-reported rather than dismissed or falsely verified.

**Portability requirement:** the regular ChatGPT/Claude guide must work as ordinary conversation, using short numbered choices and typed answers without skills installation, terminals, Tatastu tools, connectors or native widgets. Developer installation and operator checks remain a separate entry point and optional scope, not prerequisites or extra intake for ordinary users. Both are generated/maintained from the same core guidance, not separate security-policy forks.

**Later, if justified:** a small app window can render the same questions as real controls and show progress. It remains deferred until pilot evidence supports building it. Choice controls must not become action approvals; any future automation needs its own permission enforcement outside the model. The app must not be required to continue using the chat guide or developer skill.

## Delivery order: skills and chat guides first

The agreed first product is the skill plus the ordinary Claude/ChatGPT guide—not a dashboard. Follow [the rollout plan](ROLLOUT-PLAN.md): finish the small pilot package, establish safety and real-host behavior, run a founder sitting and a 3–5-person usability pilot, fix friction, then publish a maintained beta. Funding can follow evidence of use and must not block a free/manual path.

The existing versioned references are the initial resources library. A reviewed, sanitized founder story is optional context. A separate UI, database or connector is deferred until observed user problems justify it; write-capable automation requires a separate scope and consent-enforcement design. Pilot package 0.1.0-pilot.6 uses a shared intake specification with meaningful answers, per-question purposes, minimal collection, honest host-privacy limits and separate explanation/technical-scope adaptation. It retains assessment-first discovery and consistent question controls. Starting the review is not a commitment to change tools or settings. Available model review and Codex checks are documented with their limits; consumer-host acceptance is blocked and external human review remains unperformed. The next work is clearing those review/host gates through synthetic rehearsals, not website construction.

## Borrow Hallmark's simplicity, not its design product

Hallmark presents an easy install, a recognizable starting prompt, guided stages and checks before claiming a result. Apply that pattern here:

1. **Get started:** download a guide or install a skill.
2. **Understand the person:** safety, scope, explanation preference, relevant technical responsibilities, current protections, recovery, account categories, platforms, needs and constraints. Use the shared question bank: why the fact matters, substantive answers, minimum collection and assessment consequence. Collect non-secret reports one question at a time; do not pitch a product or setup during discovery. Explain that the guide adds no separate collection database but the host/model provider processes and may retain messages; no blanket no-storage promise.
3. **Assess:** explain strengths, gaps, unknowns, priorities and reasoning. An early assessment is provisional, not a demand for exhaustive disclosure.
4. **Compare and choose:** offer tailored paths with effort, cost, disruption and remaining gaps, including no changes. Then separately choose assessment only, self-directed checklist, guided walkthrough or genuinely available scoped tool assistance.
5. **Execute only if chosen:** get specific permission for each inspection/change; guide one approved step at a time with non-secret evidence. Path selection is not action authorization.
6. **Keep it useful:** preserve phase, choices, uncertainty and next step in a minimal private handoff. Assessment-only is a successful outcome, not an unfinished conversion.

If a simple distribution page is needed at public release, it should give equal prominence to **Use with any AI chat** and **Install for a coding agent**; it is not a prerequisite to the private pilot or authorization to build a dashboard. A one-command public installer needs a real reviewed public release first; do not publish a placeholder command that clones this private repository. There is no website implementation in this package.

## Lessons generalized from the earlier tune-up

The useful pattern was recovery-first account hardening, not copying one person's providers or domain arrangement. Email and SSO can unlock many other accounts; inaccessible login addresses and domain expiry can become recovery risks. Login changes must be distinguished from billing changes, and requests from completed confirmations. Aliases are organizational tools, not protection against an already-compromised receiving inbox. Domain/mail changes require continuity checks, dependencies and rollback.

A subsequently supplied incident-response export adds another lesson: private storage, activation, actual use and old-access retirement are different milestones. The [generalized incident lessons](INCIDENT-LESSONS.md) inform a consumer breach-notice path and an optional operator section; they do not make this product a forensic or autonomous incident-response service.

Historical plans mix proposals, attempts and recorded completions. None is current proof. Personal addresses, domains, account names, balances, screenshots and conversation exports are deliberately excluded. The broader checklist adds general preventive guidance; it does not imply all these controls were part of or completed in that earlier tune-up.

## Guided setup, not a recommendation dump

Ask one short question at a time; branch on devices, existing password storage, recovery, budget, accessibility and country. Preserve adequate existing tools. When a manager is needed, help the person choose, set it up privately, preserve recovery and complete a first useful login before broader rollout. Keep all 21 coverage areas tracked behind the scenes and never hide skipped or unknown areas.

The same core works internationally; identity/credit/reporting modules require current local evidence. See [RESEARCH.md](RESEARCH.md) and [the second review and staged plan](RESEARCH-PASS-2.md) for evidence and limits. The preferred new paid/sponsored manager path is now 1Password, with its own recovery/setup branch. This is a product choice, not an independent finding of vendor superiority. Its nonprofit page advertises possible credits/support, but eligibility and recipient funding remain unconfirmed. Preserve adequate existing tools and a free path.

Sponsorship should fund recipient-owned access, not give the project or sponsor personal vault/recovery control. Confirm duration, costs/renewal consent, data handling and continuation/exit before offering support. Other prospective roles remain National Cybersecurity Alliance for education/distribution, Bitwarden as a free-core alternative, FIDO Alliance for authentication education, and Access Now for eligible civil-society escalation. No outreach or account integration has occurred.

## Public-good commitments

- Core guide and skill should be free to obtain; licensing must be settled before public release.
- No required account at this project, no collection of audit reports, no tracking in the package.
- No affiliate-driven default recommendations or mandatory security-product purchases.
- Use built-in protections and maintain a viable free path; a preferred paid manager is optional, with costs, recovery and funding-end trade-offs explained.
- Plain language, small steps, accessible pacing and region-appropriate identity guidance.
- Honest limits: AI can make mistakes; providers change; high-risk incidents need human specialists.
- Local files are not a privacy guarantee: the chosen AI host still processes conversation data.

## Release gates

Before calling it publicly available: choose a public home/name and license; independently review the security guidance; exercise both the regular-chat and developer-host paths with synthetic data; check for personal information; provide release/version notes and a correction channel; confirm the download and install work from a clean environment.

Keep any eventual public source limited to this generic package. Do not publish this repository or its history. Measure usefulness through voluntary, non-sensitive feedback, not recovery maps, credential collection, a fabricated security score or unsupported prevention claims.
